# CognoDB Cloud vs. Managed Graph Databases — A Reproducible Benchmark (Go)

> Wexa AI take-home: benchmark CognoDB Cloud against four other managed graph database platforms on identical data, identical workloads, and matched resource tiers — and report the results honestly, caveats included.

**Author:** Suresh · **Repo purpose:** technology-evangelism take-home for Wexa AI  
**Language:** Go  
**Benchmark status:** CognoDB Cloud completed; Neo4j AuraDB, Memgraph, FalkorDB, and ArangoDB are pending final runs.

---

## TL;DR

- **Dataset:** [SNAP `email-Enron`](https://snap.stanford.edu/data/email-Enron.html) — 36,692 nodes. The current benchmark pipeline loads **367,662 relationships** from the prepared dataset. The raw SNAP source contains 183,831 directed edges; the prepared dataset's relationship count should be interpreted according to the transformation performed by `cmd/prepare-dataset`.
- **Platforms:** CognoDB Cloud (given), Neo4j AuraDB Free, Memgraph, FalkorDB, ArangoDB. Rationale for each is in [Platform selection](#platform-selection).
- **Resource parity:** CognoDB's advertised c0 tier is the reference point: **0.5 vCPU (burstable), 256 MB RAM, 1 GB disk**. Other platforms are matched as closely as their available tier or local container allows, with disclosed exceptions.
- **One binary, protocol-based adapters:** `internal/dbclient/` implements one `GraphClient` interface per wire protocol rather than one implementation per vendor. `cmd/run-benchmark` is the single benchmark program used across platforms.
- **Minimal dependencies:** the database drivers are the only external runtime dependencies; configuration parsing and SVG chart generation are implemented in the repository.
- **Results:** generated by `go run ./cmd/build-report` from the raw JSON files in `results/raw/`.

## Platform selection

The brief leaves the choice of comparison platforms open, on purpose — that choice is part of what's being evaluated.

| Platform | Why it's in this benchmark |
|---|---|
| **CognoDB Cloud** | The subject of the assignment. Speaks Bolt + Cypher, so compatibility with the Neo4j Go driver can be tested directly. |
| **Neo4j AuraDB Free** | The natural reference point because CognoDB's connection/query model is Neo4j-compatible. |
| **Memgraph** | Bolt-compatible and Cypher-native, providing a same-protocol/query-language comparison against a different graph engine. |
| **FalkorDB** | Uses the Redis protocol with a Cypher-compatible query layer, testing the benchmark across a different transport and storage architecture. |
| **ArangoDB** | Uses AQL rather than Cypher, so the logical workloads must be expressed in a genuinely different query language. |

All five are intended to be either managed/free-tier deployments or self-hosted deployments capped to approximately the reference resources. `internal/config/platforms.go` records the configured path for each platform.

## Dataset

**[SNAP `email-Enron`](https://snap.stanford.edu/data/email-Enron.html)** — email communication graph from the Enron corpus (Leskovec, Kleinberg, Faloutsos, KDD 2005).

The raw SNAP dataset contains **36,692 nodes and 183,831 directed edges**. The current benchmark pipeline produces a prepared dataset that results in **367,662 loaded relationships**. Because that relationship count is produced by the repository's preprocessing/loading pipeline, it should not be described as the raw SNAP edge count.

The dataset was chosen over the full SNAP `soc-Pokec` graph because Pokec is much larger and would require aggressive sampling to fit the smallest resource tier. `email-Enron` is a real-world graph at a scale that can be loaded consistently across small environments without introducing arbitrary sampling rules.

### Data preparation and loading

Identical input files are used for every platform:

1. `bash data/download_dataset.sh` fetches the raw SNAP edge list.
2. `go run ./cmd/prepare-dataset` creates the repository's normalized `data/nodes.csv` and `data/edges.csv`.
3. Each platform adapter reads those files and loads them using its official Go driver in batches.

### Data loading method per platform

| Platform | Load method |
|---|---|
| CognoDB / Neo4j AuraDB / Memgraph | `neo4j-go-driver`, `UNWIND $batch AS row CREATE ...` in batches of 1,000 (configurable with `--batch-size`) |
| FalkorDB | `falkordb-go`, batched Cypher over the Redis protocol |
| ArangoDB | `arangodb/go-driver/v2`, `collection.CreateDocuments()` in batches of 1,000 |

No platform uses a bulk-import file tool such as `neo4j-admin import` or `arangoimport`. Driver-based loading is used consistently so the ingest measurement includes comparable client/driver round trips.

## Architecture

```text
data/download_dataset.sh    -> data/email-Enron.txt (raw SNAP edge list)
cmd/prepare-dataset/main.go -> data/nodes.csv, data/edges.csv (shared input for every platform)

internal/dbclient/client.go       -> GraphClient interface every adapter implements
internal/dbclient/cypherbolt.go   -> CognoDB, Neo4j AuraDB, Memgraph (shared Bolt+Cypher path)
internal/dbclient/falkordb.go     -> FalkorDB (Redis protocol, Cypher-compatible path)
internal/dbclient/arangodb.go     -> ArangoDB (AQL)
internal/dbclient/factory.go      -> builds the correct client from config + .env

internal/config/platforms.go -> static platform registry: specs, dialect, env prefix, caveats
internal/config/config.go    -> dependency-light .env loader + benchmark configuration

internal/harness/runner.go -> load -> warm up -> measure -> results/raw/<platform>_<timestamp>.json
internal/harness/stats.go  -> shared percentile calculations

internal/report/report.go -> results/raw/*_latest.json -> results/RESULTS.md
internal/report/charts.go -> hand-rolled SVG charts

cmd/run-benchmark/main.go -> benchmark CLI
cmd/build-report/main.go  -> report/charts generator
```

The adapter-per-protocol design is deliberate. CognoDB, Neo4j AuraDB, and Memgraph share the same Bolt/Cypher client path, while FalkorDB and ArangoDB use their own protocols/dialects. Exact logical query definitions are documented in `docs/QUERIES.md`.

### Mixed-workload concurrency

`internal/harness/runner.go` uses Go goroutines, channels, and `sync.WaitGroup` to create the requested concurrency levels. Each concurrent worker uses its own database client connection. No external worker-pool package is required.

### Dependency choices

The benchmark keeps the dependency surface small: database drivers are used where required, while configuration parsing and SVG chart generation are implemented locally rather than adding dedicated dotenv or plotting libraries.

## Fairness & resource parity

CognoDB's free `c0` tier is the reference point: **0.5 vCPU (burstable), 256 MB RAM, 1 GB disk**.

| Platform | vCPU | RAM | Disk | How it was matched |
|---|---:|---:|---:|---|
| CognoDB Cloud | 0.5 (burstable) | 256 MB | 1 GB | Reference tier |
| Neo4j AuraDB Free | Verify on provisioned instance | Verify | Verify | Exact free-tier compute limits are not assumed; record observed/provided values before final comparison |
| Memgraph | 0.5 | 256 MB | 1 GB | Self-hosted container cap in `docker-compose.yml` unless a managed instance is used |
| FalkorDB | 0.5 | 256 MB | 1 GB | Self-hosted container cap in `docker-compose.yml` unless a managed instance is used |
| ArangoDB | 0.5 | **512 MB** | 1 GB | 512 MB is the stable local cap used for the benchmark because 256 MB was not sufficient to complete loading reliably |

### Disclosed resource exception

ArangoDB uses **512 MB RAM instead of 256 MB** because the 256 MB container was not stable enough to complete the dataset load under the tested RocksDB configuration. Reporting an incomplete run as if it were comparable would be less honest than disclosing the memory difference.

## How to reproduce

```bash
git clone <this-repo-url>
cd cognodb-graph-benchmark

# First-time Go dependency setup.
# If go.sum is absent, this generates it from the pinned go.mod versions.
go mod tidy

cp .env.example .env
# Edit .env with the credentials/URIs for the platforms you will run.

# Prepare the common dataset.
bash data/download_dataset.sh
go run ./cmd/prepare-dataset

# Optional: start self-hosted comparison services.
docker compose up -d memgraph falkordb arangodb

# Run each platform independently.
go run ./cmd/run-benchmark --platform cognodb    --fresh
go run ./cmd/run-benchmark --platform neo4j_aura --fresh
go run ./cmd/run-benchmark --platform memgraph   --fresh
go run ./cmd/run-benchmark --platform falkordb   --fresh
go run ./cmd/run-benchmark --platform arangodb   --fresh

# Rebuild the results matrix and charts.
go run ./cmd/build-report
```

Each `run-benchmark` invocation loads the shared dataset, optionally clears the target database, creates indexes, warms up the workload, executes the benchmark suite, and writes both a timestamped JSON file and a `<platform>_latest.json` file under `results/raw/`.

### Benchmark methodology

- **Read iterations:** 100 measured iterations after a 20-iteration warm-up, configurable with `BENCH_ITERATIONS` and `BENCH_WARMUP`.
- **Traversal sampling:** 50 distinct random start nodes per hop depth.
- **Cold-start measurement:** the first call before warm-up is recorded separately.
- **Mixed workload:** 80% reads / 20% writes at concurrency levels 1, 10, and 40 for 30 seconds per step.
- **Percentiles:** p50, p95, and where applicable p99 are calculated by the same shared statistics code for every platform.

### Building standalone binaries

```bash
go build -o bin/prepare-dataset ./cmd/prepare-dataset
go build -o bin/run-benchmark   ./cmd/run-benchmark
go build -o bin/build-report    ./cmd/build-report
```

## Analysis

### Current CognoDB observations

- **Ingest:** the completed CognoDB run loaded the prepared dataset in **114.60 seconds**, at **320.2 nodes/s** and **3,208.1 relationships/s**.
- **Traversal scaling:** p50 latency increased from **245.76 ms at 1 hop** to **255.46 ms at 2 hops** and **438.81 ms at 3 hops**. The 3-hop p95 of **766.05 ms** is substantially higher, showing a heavier tail as traversal depth increases.
- **Lookups:** point lookup p50 was **259.01 ms**, while indexed range lookup p50 was **273.94 ms**. The relatively small difference indicates that both workloads are operating in a similar latency range in this environment.
- **Aggregation:** the top-10-by-out-degree aggregation was substantially slower than the lookup and traversal workloads, at **1,573.21 ms p50** and **1,715.40 ms p95**.
- **Mixed workload:** throughput increased from **4.03 QPS at concurrency 1** to **39.17 QPS at concurrency 10**, approximately tracking the 10x concurrency increase in this range.
- **Concurrency 40:** the highest-concurrency step failed before producing a valid throughput measurement because the client timed out while waiting for a connection to the CognoDB Bolt endpoint. The failure is retained as a result rather than replaced with a synthetic value.

### Cross-platform analysis

A final cross-platform ranking should only be written after Neo4j AuraDB, Memgraph, FalkorDB, and ArangoDB have completed the same benchmark suite. At that point, compare:

- ingest throughput;
- 1/2/3-hop p50 and p95 scaling;
- point vs. indexed lookup cost;
- aggregation latency;
- mixed-workload throughput and scaling;
- storage footprint where directly observable; and
- the effect of different query dialects and deployment/network paths.

## Caveats — read this before trusting a number

- **Current results are incomplete across the five-platform set.** CognoDB Cloud is the only platform with a completed benchmark in the current repository state. The other four platforms remain marked `Pending` until their runs are executed.
- **Mixed workload concurrency 40 failed on CognoDB.** The failure was a connection timeout while waiting for a connection to the Bolt endpoint. It is reported explicitly and is not converted into a latency or throughput number.
- **Free-tier throttling and connection limits are outside the benchmark's full control.** Small managed instances can exhibit CPU throttling, connection limits, or transient resource pressure under sustained concurrent load. These behaviors are part of the observed platform result and should not be silently normalized away.
- **Network variance matters.** Managed cloud databases are reached over the public internet, while self-hosted Docker containers run locally. Absolute latency comparisons across those deployment types therefore include a network-path difference. Relative scaling and workload shape are more informative than treating every absolute millisecond value as a pure engine comparison.
- **Query-language differences matter.** CognoDB, Neo4j, and Memgraph use Bolt/Cypher-compatible workloads; FalkorDB uses its Redis/Cypher path; ArangoDB uses AQL. The benchmark targets logical equivalence, not byte-identical query text across all engines.
- **ArangoDB uses 512 MB RAM.** This is the documented fairness exception described in [Fairness & resource parity](#fairness--resource-parity).
- **Free-tier resource specifications are not always directly comparable.** Where an exact cloud-tier CPU/RAM number is not published or observable, the README reports that limitation rather than inventing a specification.
- **Bulk import is intentionally not used.** All platforms use driver-mediated loading so that the benchmark measures comparable application-to-database ingest behavior rather than mixing network/driver loading with local bulk-import utilities.
- **Go dependencies:** run `go mod tidy` on a normal internet-connected machine if `go.sum` is missing, and commit the generated `go.sum` before the final submission.
- **Results are generated artifacts.** `results/RESULTS.md` and `results/charts/` should be regenerated with `go run ./cmd/build-report` after the final platform runs rather than manually editing generated values.
