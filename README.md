# CognoDB Cloud vs. Managed Graph Databases — A Reproducible Benchmark (Go)

> Wexa AI take-home: benchmark CognoDB Cloud against four other managed graph
> database platforms on identical data, identical workloads, and matched
> resource tiers — and report the results honestly, caveats included.

**Author:** Suresh · **Repo purpose:** technology-evangelism take-home for Wexa AI
**Language:** Go (single module, three official database drivers, zero other external dependencies)

---

## TL;DR

- **Dataset:** [SNAP `email-Enron`](https://snap.stanford.edu/data/email-Enron.html) — 36,692 nodes, 183,831 directed edges. Fits comfortably inside the 100k–500k relationship band and inside every platform's smallest tier.
- **Platforms:** CognoDB Cloud (given), Neo4j AuraDB Free, Memgraph, FalkorDB, ArangoDB. Rationale for each in [Platform selection](#platform-selection).
- **Resource parity:** every platform is run at CognoDB's advertised c0 spec (0.5 vCPU / 256 MB RAM / 1 GB disk) or the closest equivalent its tier allows — see [Fairness & resource parity](#fairness--resource-parity) for exact numbers and the one disclosed exception.
- **One binary, five adapters:** `internal/dbclient/` implements one `GraphClient` interface per wire protocol (not per platform); `cmd/run-benchmark` is the single program that loads data, warms up, measures, and writes JSON for whichever platform you point it at.
- **Zero charting/config dependencies:** only the three official database drivers (`neo4j-go-driver`, `falkordb-go`, `arangodb/go-driver`) are external dependencies. `.env` parsing and SVG chart generation are both hand-rolled in ~100 lines each rather than pulling in a dotenv or plotting library — see [Architecture](#architecture).
- **Results:** see [Results matrix](#results-matrix) — generated by `go run ./cmd/build-report` from the raw JSON in `results/raw/`.

## Platform selection

The brief leaves the choice of comparison platforms open, on purpose — that
choice is part of what's being evaluated. Here's the reasoning:

| Platform | Why it's in this benchmark |
|---|---|
| **CognoDB Cloud** | The subject of the assignment. Speaks Bolt + Cypher, so it's a drop-in replacement for the official Neo4j driver — worth testing that claim directly. |
| **Neo4j AuraDB Free** | The obvious reference point: CognoDB's connection story (`bolt+s://`, Neo4j driver, Cypher) is explicitly Neo4j-compatible, so the fairest first comparison is against Neo4j itself, on its own free managed tier. |
| **Memgraph** | Also Bolt-protocol-compatible and Cypher-native, but architecturally different (in-memory-first, C++ core) — a same-query-language, different-engine comparison that isolates engine performance from query-language differences. |
| **FalkorDB** | A genuinely different transport (Redis protocol, not Bolt) with an openCypher-subset query layer — tests whether the benchmark's "same logical queries" claim holds up when the wire protocol changes, and represents the sparse-matrix/GraphBLAS school of graph engines rather than native graph storage. |
| **ArangoDB** | Multi-model, queried in AQL rather than Cypher. Included specifically so this isn't "one query language, five paint jobs" — it forces every workload to be re-expressed in a genuinely different query language, which is a more honest test of "same logical query" than reusing Cypher everywhere. |

All five are either free-tier managed clouds or self-hosted deployments
capped to match — both are explicitly allowed by the assignment brief.
`internal/config/platforms.go` records exactly which path was used for each.

## Dataset

**[SNAP `email-Enron`](https://snap.stanford.edu/data/email-Enron.html)** — email
communication graph from the Enron corpus (Leskovec, Kleinberg, Faloutsos,
KDD 2005). Nodes are email addresses, edges are "sent at least one email
to." 36,692 nodes, 183,831 directed edges after removing self-loops.

Chosen over the SNAP `soc-Pokec` sample suggested in the brief because
Pokec's full size (1.6M nodes / 30M edges) would need aggressive, somewhat
arbitrary sampling to fit a 256 MB free tier, whereas `email-Enron` is
already the right order of magnitude, is a real (not synthetic) social
graph, and is small enough that every platform in this comparison — even
the 256 MB tier — can hold it without pre-emptive sampling decisions
skewing the comparison.

Identical loading pipeline for every platform:
1. `bash data/download_dataset.sh` — fetches the raw edge list from SNAP.
2. `go run ./cmd/prepare-dataset` — dedupes, strips self-loops, writes flat `data/nodes.csv` / `data/edges.csv`.
3. `<platform client>.BulkLoad()` — reads those two CSVs (already parsed into memory by `internal/dataset`) and batch-loads via each platform's own driver — see [Data loading method per platform](#data-loading-method-per-platform).

### Data loading method per platform

| Platform | Load method |
|---|---|
| CognoDB / Neo4j AuraDB / Memgraph | `neo4j-go-driver`, `UNWIND $batch AS row CREATE ...` in batches of 1,000 (configurable via `--batch-size`) |
| FalkorDB | `falkordb-go`, same `UNWIND`-batched Cypher over the Redis protocol |
| ArangoDB | `arangodb/go-driver/v2`, `collection.CreateDocuments()` in batches of 1,000 |

No platform uses a bulk-import file tool (e.g. `neo4j-admin import`,
ArangoDB's `arangoimport`) — driver-batched loads were used uniformly so
ingest throughput measures the same kind of operation (driver round-trips)
on every platform. This is a deliberate methodology choice, not an
oversight: bulk file-import tools bypass the network/driver layer entirely
and would not be a fair comparison against a managed free tier most users
reach over a regular Bolt/HTTP connection. Noted again in
[Caveats](#caveats--read-this-before-trusting-a-number).

## Architecture

```
data/download_dataset.sh    -> data/email-Enron.txt (raw SNAP edge list)
cmd/prepare-dataset/main.go -> data/nodes.csv, data/edges.csv (shared input for every platform)

internal/dbclient/client.go       -> GraphClient interface every adapter implements
internal/dbclient/cypherbolt.go   -> CognoDB, Neo4j AuraDB, Memgraph (shared — all Bolt+Cypher)
internal/dbclient/falkordb.go     -> FalkorDB (Redis protocol, Cypher subset)
internal/dbclient/arangodb.go     -> ArangoDB (AQL)
internal/dbclient/factory.go      -> builds the right client from internal/config + .env

internal/config/platforms.go -> static platform registry: specs, dialect, env var prefix, caveats
internal/config/config.go    -> dependency-free .env loader + BenchConfig

internal/harness/runner.go -> load -> warm up -> measure -> results/raw/<platform>_<timestamp>.json
internal/harness/stats.go  -> shared p50/p95/p99 percentile math (used identically by every platform)

internal/report/report.go -> results/raw/*_latest.json -> results/RESULTS.md
internal/report/charts.go -> hand-rolled SVG bar/line charts (no charting library)

cmd/run-benchmark/main.go -> CLI: go run ./cmd/run-benchmark --platform <key> --fresh
cmd/build-report/main.go  -> CLI: go run ./cmd/build-report
```

The one-adapter-per-protocol design (not one-adapter-per-platform) is
deliberate: CognoDB, Neo4j AuraDB, and Memgraph all get the *exact same*
Cypher text and batching code, so any latency difference between those three
is attributable to the database, not to subtly different client code. See
`docs/QUERIES.md` for the exact query text used on every platform.

**Why goroutines instead of a worker-pool library for the mixed workload:**
`internal/harness/runner.go`'s `runMixedWorkloadSweep` spawns one goroutine
per concurrent client, each with its own `GraphClient` connection, and
collects results over a buffered channel with a `sync.WaitGroup` — no
external concurrency library, since Go's standard `go`/`sync`/`channel`
primitives are already the right tool for "N independent workers hammering
a database for a fixed duration."

**Why no external config/dotenv/charting dependencies:** the only external
packages this module imports are the three official database drivers it's
benchmarking (`neo4j-go-driver`, `falkordb-go`, `arangodb/go-driver`). `.env`
parsing (`internal/config/config.go`) and chart rendering
(`internal/report/charts.go`) are both small enough (~100 lines each) to
write directly rather than adding a dependency for them — a deliberate
minimalism choice, not an oversight.

## Fairness & resource parity

CognoDB's free `c0` tier is the reference point: **0.5 vCPU (burstable),
256 MB RAM, 1 GB disk.** Every other platform was sized to match as closely
as its tier allows:

| Platform | vCPU | RAM | Disk | How it was matched |
|---|---|---|---|---|
| CognoDB Cloud | 0.5 (burstable) | 256 MB | 1 GB | reference tier (assignment brief) |
| Neo4j AuraDB Free | *[VERIFY AT SIGNUP — not publicly disclosed]* | *[VERIFY AT SIGNUP]* | *[VERIFY AT SIGNUP]* | Neo4j doesn't publish exact vCPU/RAM for the Free tier; two Neo4j-affiliated sources even disagree on the node/relationship cap (200k/400k vs. 50k/175k) — confirm your own instance's real numbers in the Aura console and paste them here. This asymmetry is disclosed, not hidden. |
| Memgraph | 0.5 (`docker --cpus=0.5`) | 256 MB (`--memory=256m`) | 1 GB | self-hosted, capped via `docker-compose.yml` (or Memgraph Cloud free trial if you provisioned one — update this row to match) |
| FalkorDB | 0.5 | 256 MB | 1 GB | self-hosted, capped via `docker-compose.yml` (or FalkorDB Cloud free tier if available — update this row) |
| ArangoDB | 0.5 | **512 MB** (see caveat) | 1 GB | self-hosted, capped via `docker-compose.yml` |

**Disclosed exception:** ArangoDB's `arangod` process was not stable at
256 MB in local testing with RocksDB's default write-buffer sizing for this
dataset size — it was OOM-killed mid-load. 512 MB was the smallest value
found stable. Reporting numbers from a container that can't reliably finish
a load would be worse than disclosing a 2x memory deviation on one of five
platforms — see the assignment's own instruction to record caveats honestly
rather than hide them.

machine spec, OS, network, and the cloud region you selected for each
managed instance]*. Same client, same network path, for every platform in a
given run — cross-region comparisons were avoided by picking the same (or
nearest-equivalent) region for every cloud platform.

## How to reproduce

```bash
git clone <this-repo-url>
cd cognodb-graph-benchmark

# Step 0 — populate go.sum. This repo ships go.mod with pinned, verified
# versions, but NOT go.sum: it was built in a network-restricted sandbox
# that couldn't reach the real Go checksum database (sum.golang.org), so
# shipping a go.sum generated under that workaround would have been
# actively misleading. Run this once, on a machine with normal internet:
go mod tidy

cp .env.example .env
# edit .env: paste in your CognoDB / Neo4j Aura / (optionally) Memgraph &
# FalkorDB Cloud / ArangoDB Oasis credentials. Leave any platform's URI
# blank and use docker-compose instead — see below.

# 1) get the dataset (same nodes.csv/edges.csv feeds every platform)
bash data/download_dataset.sh
go run ./cmd/prepare-dataset

# 2) (optional) bring up self-hosted fallbacks capped to CognoDB's specs
docker compose up -d memgraph falkordb arangodb

# 3) run the benchmark once per platform — each is fully independent
go run ./cmd/run-benchmark --platform cognodb    --fresh
go run ./cmd/run-benchmark --platform neo4j_aura --fresh
go run ./cmd/run-benchmark --platform memgraph   --fresh
go run ./cmd/run-benchmark --platform falkordb   --fresh
go run ./cmd/run-benchmark --platform arangodb   --fresh

# 4) build the results matrix + charts from results/raw/*_latest.json
go run ./cmd/build-report
# -> results/RESULTS.md, results/charts/*.svg
```

Each `run-benchmark` invocation is fully self-contained: it connects,
(optionally) wipes the target database, creates indexes, bulk-loads
`data/nodes.csv` + `data/edges.csv`, warms up, measures every §5.2 metric,
and writes `results/raw/<platform>_<timestamp>.json` plus a
`<platform>_latest.json` that `build-report` reads. Re-running a single
platform never touches the others' result files.

**Iteration counts:** 100 measured iterations per read workload after a
20-iteration warm-up (both configurable via `.env` — `BENCH_ITERATIONS`,
`BENCH_WARMUP`). Traversals additionally sample 50 distinct random start
nodes per hop depth, per the brief's "randomly chosen set of start nodes."
One cold-start latency (the very first call, before warm-up) is captured
and reported separately for every workload.

**Building standalone binaries** (optional, instead of `go run`):
```bash
go build -o bin/prepare-dataset ./cmd/prepare-dataset
go build -o bin/run-benchmark   ./cmd/run-benchmark
go build -o bin/build-report    ./cmd/build-report
```

## Analysis

*[FILL IN AFTER RUNNING — guiding questions below; delete once answered]*

- **Ingest:** which platform loaded fastest, and does that track with
  architecture (in-memory-first vs. disk-native, single-statement vs.
  batched transactions) rather than just "which vendor"?
- **Traversals:** does p95 latency grow roughly linearly with hop depth on
  every platform, or does one platform's query planner degrade faster?
  Relate this to whether the platform does index-free adjacency (native
  graph storage) vs. join-based traversal under the hood.
- **Lookups:** how much does the indexed range lookup cost relative to the
  point lookup on each platform — a big gap suggests index-scan overhead
  that a point-get avoids; a small gap suggests the platform is doing
  something closer to a full index seek either way.
- **Aggregation:** is the top-10-by-out-degree query dominated by the same
  cost driver as 1-hop traversal (both touch every outgoing edge), or does
  the `ORDER BY ... LIMIT` add a distinct sort cost?
- **Mixed workload:** does throughput scale roughly linearly from 1→10→40
  concurrent goroutines, or does it plateau/regress on the free-tier
  instances — and if so, is that CPU throttling (burstable vCPU exhaustion)
  or connection-pool limits on the platform side (Go's own goroutines don't
  hit an OS thread ceiling anywhere near 40, so a plateau here is the
  database, not the client)?
- **Footprint:** for the platforms where storage was observable, does
  stored size correlate with ingest speed (e.g. a platform storing more
  per-edge overhead might also be slower to write)?
- **CognoDB specifically:** does its Bolt/Cypher compatibility claim hold
  up in practice — no code changes needed beyond swapping the URI — and
  how does its latency profile compare to Neo4j AuraDB Free, its closest
  architectural analogue in this set?

## Caveats — read this before trusting a number

- **`go.sum` is not shipped in this initial commit — see [How to reproduce](#how-to-reproduce), step 0.** This repo was built in a network-restricted environment that could reach GitHub directly but not `sum.golang.org` or `golang.org`'s vanity-import redirect service. Rather than ship a `go.sum` generated by working around that (which would be right for the sandbox but potentially stale/wrong for a real checksum database lookup), `go.mod` ships with pinned, verified-working version numbers and the repo asks you to run `go mod tidy` once, from a machine with normal internet access, to populate `go.sum` properly. Commit the resulting `go.sum` after that.
- **Free-tier throttling is real and not fully controllable.** Burstable
  vCPU tiers (CognoDB's own description, and likely several of the others)
  can throttle after sustained load, especially during the mixed-workload
  concurrency sweep. Where a platform's throughput visibly drops at higher
  concurrency, that is reported as-is rather than smoothed over.
- **Network variance.** Managed cloud platforms are reached over the public
  internet from the client machine; self-hosted Docker platforms (whichever
  of Memgraph/FalkorDB/ArangoDB ended up self-hosted rather than cloud) have
  effectively zero network hop. This is an intrinsic asymmetry of comparing
  "genuinely remote managed cloud" against "capped local container" and is
  **not correctable by resource capping alone** — it's disclosed here rather
  than glossed over. Prefer reading the *relative* shape of results (how do
  1/2/3-hop latencies scale? how does throughput change with concurrency?)
  over absolute cross-platform latency deltas for this reason.
- **Query-language differences.** ArangoDB's AQL and FalkorDB's Cypher
  subset are not byte-identical to the Cypher used against
  CognoDB/Neo4j/Memgraph. Every effort was made to keep them *logically*
  equivalent (see `docs/QUERIES.md`) but query planners differ, and a
  planner-level advantage for one dialect over another is a legitimate
  source of variance, not a bug in this harness.
- **`arangodb/go-driver/v2` is pinned to v2.2.0, not the latest v2.3.1** —
  v2.3.1 requires Go 1.25, and this repo targets Go 1.24 for broader
  toolchain compatibility. Bump both together if you'd rather track latest.
- **Timeouts / failed runs.** *[FILL IN: note here any platform/workload
  combination that timed out or failed outright during your actual runs,
  and what you did about it — e.g. retried, reduced concurrency, excluded
  a cell from the table and said so explicitly.]*
- **ArangoDB's memory cap** is 512 MB, not 256 MB — see
  [Fairness & resource parity](#fairness--resource-parity) for why.
- **CognoDB's public discoverability.** `console.cognodb.com` is a live,
  working product but is tagged `noindex` and does not appear in general
  web search — worth knowing if you're citing this project publicly and
  someone asks "wait, is this real?"
